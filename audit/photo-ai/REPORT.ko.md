**현재 데이터 재확인 — 집계 범위가 중요합니다**

다음은 공개 API의 RLS가 허용한 행에서 확인한 수치입니다. 운영 DB 전체 건수, 수령 완료 행 전체, 실제 분석 성공 건수로 읽으면 안 됩니다.

`IMAGE_URL_HOSTS`의 실제 구현은 정확한 호스트뿐 아니라 그 하위 도메인도 허용합니다. README의 “정확한 호스트” 설명만으로 완전 일치 정책이라고 이해하면 안 됩니다. HTTPS·인증정보·비표준 포트·리다이렉트 호스트 검사는 존재합니다. 새 작업자의 경로 검사와 기존 ai-parse의 호스트 검사를 모두 통과해야 합니다.

**재검증 결과 맞는 부분도 있습니다**

- 저장소의 두 AI 함수에는 `SUPABASE_SERVICE_ROLE_KEY`와 Bearer 값을 비교하는 서버 호출 경로가 있습니다. worker가 보내는 Bearer와 apikey 방식은 이 소스와 맞습니다. 실제 운영 배포본·게이트웨이 JWT 설정까지 확인한 것은 아닙니다.
- Gemini 호출은 Google `generateContent`에 `x-goog-api-key` 헤더를 사용합니다. 키를 URL에 넣지 않습니다. 실제 모델 ID·키 유효성·할당량·응답은 검증하지 않았습니다.
- 코어 C안 마이그레이션은 브랜치 초기 스키마 위의 로컬 PostgreSQL에서 실행됐습니다. 모든 SQL이 문법적으로 틀린 것은 아닙니다. 사전 점검 오류와 운영 호환성을 구분해야 합니다.
- 로컬에서 정상 완료, 중복 완료 거부, 5분/15분 재시도와 세 번째 실패, 사진 경로 변경 후 오래된 lease 거부, 수령 완료 후 결과 반영 거부가 동작했습니다.
- 정상 완료 시 원래 `items.description`과 기존 `owner_check_memo`는 보존됐습니다. 기본 이미지·빈 경로 제외도 로컬에서 동작했습니다.
- 원본 worker가 저장하는 특징은 제한된 일반 태그이며, 시민 공개 설명에 직접 쓰지 않습니다. 그러나 `done`은 AI 처리 완료일 뿐 사람 검토 완료가 아닙니다.

사진 바이트 자체는 기존 ai-parse에서 가림 없이 Gemini에 전송됩니다. 기존 마스킹은 텍스트에 적용되며 이미지 속 개인정보를 사전 삭제하지 않습니다. 또한 사진 버킷은 초기 SQL에서 공개 버킷으로 설정됩니다. 결과를 비공개 DB에 저장하는 것과 원본 사진의 공개·외부 전송 범위는 구분해야 합니다. 이번 작업에서는 버킷 공개 설정을 바꾸지 않았습니다.

현재 색상·분류·특징 허용표는 프로젝트 내부 규칙입니다. 공식 코드표의 출처·버전·원본 API 코드 대응을 확인했다는 근거는 ZIP에 없습니다. AI가 코드표에 있는 단어를 반환해도 사진 내용이 사실이라는 증거가 되지는 않습니다.

기존 화면은 `item_private(owner_check_memo)`만 조회하고, 수동 버튼은 별도로 AI를 다시 호출합니다. C안을 붙여도 자동 특징 표시·담당자 검토·수동/자동 중복 방지는 완성되지 않습니다. 현재 화면 기능은 그대로 보존하고, 후속 검토 화면을 별도로 설계해야 합니다.

**수정 방향 — 운영 카탈로그 확인 후 확정할 권고안**

| 선택지 | 장점 | 비용/위험 |
| --- | --- | --- |
| C안 보완: items 상태 + item_private 결과 | 원안과 가까움 | 기존 공개 테이블·권한·updated_at·트리거에 영향을 줌. 추가 10컬럼 및 결과 보호 보완 필요 |
| 비공개 작업/결과 저장소 추가 | 기존 공개 items와 담당자 메모 구조를 보존. 큐 상태와 결과 권한을 명확히 분리 | 새 비공개 관계·서비스 전용 RPC, 담당자 검토 조회 경로가 필요 |

**권고는 두 번째 방식입니다.** 새 테이블 수가 0개인 것만으로 기존 DB 영향이 최소가 되지는 않습니다. 비공개 스키마의 작업/결과 저장소와 제한된 RPC를 추가하고, 기존 items에는 필요한 신규/변경 이벤트 연결만 하는 편이 팀원 기능 보존과 정보 노출 방지에 유리합니다. 전역 실행 제어를 위한 작은 관리 관계가 추가로 필요할 수 있습니다. 이미 유사 큐가 있다면 재사용 여부를 먼저 검토합니다.

구현 시 지킬 조건:

1. 실제 수집·AI 배포본을 저장소 SHA와 대조하고, 기존 사진 저장 기능을 재사용합니다. main이나 팀원 파일을 통째로 복사하지 않습니다.
2. 물품 ID·정규화된 사진 경로·사진 버전·분석기 버전을 작업의 식별자로 사용합니다. 동일 경로 덮어쓰기는 Storage 버전/수정 시각/ETag를 주기적으로 대조해 탐지합니다. 최종 반영 전에도 출처·상태·사진 버전을 재검증합니다.
3. 원자적 선점, lease 만료 복구, 오래된 결과 거부와 별개로 전역 동시 실행·분당 호출·일일 예산을 제한합니다. 설정 오류를 개별 물품 실패로 소진하지 않습니다.
4. 색상은 확인된 코드표의 값만, 재질·외형은 명시적 허용값만 비공개 저장합니다. AI 원본 자유 문장은 공개 설명에 합치지 않습니다. 모든 자동 결과는 사람 검토 전 상태로 둡니다.
5. 운영 기관별 RLS를 확인하고 원본 AI 결과 쓰기는 서버로 제한합니다. 담당자 검토·승인은 별도 필드와 권한 검사 경로를 사용합니다. 기존 수동 버튼이 이미 분석한 버전을 재호출하지 않도록 연동합니다.
6. 기본 이미지, 없는 객체, 크기 초과, 미지원 MIME을 모델 호출 전에 분류합니다. 크기 초과 원본을 자동 교체하거나 삭제하지 않습니다. 축소본이 필요하면 별도 경로·원본 보존 방식을 검토합니다.
7. 기존 사진 등록은 Dry Run 집계를 먼저 제시한 뒤 `ON CONFLICT DO NOTHING` 방식으로 기존 완료/실패 상태를 보존합니다. 운영 전체 백필은 1건 파일럿 검증 후에만 시작합니다.
8. 자동 실행이 꺼진 상태에서 정확한 물품 ID·사진 버전 1건만 파일럿 대상으로 제한합니다. HTTP 200이 아니라 실제 모델 호출·lease 반영·비공개 결과·공개 원문 보존·중복 재호출 차단을 확인합니다.

**백업과 복구 계획**

적용 전에 대상 테이블 정의·인덱스·정책·GRANT·트리거·RPC·Cron 명령 해시·배포 함수 버전을 기록하고, 영향받는 원본 데이터는 접근 제한된 백업으로 보존해야 합니다. 이번에는 운영 연결이 없어 백업을 만들지 않았습니다.

복구는 먼저 새 자동 실행만 중지하고, 새 작업자의 진행 중 lease를 확인한 뒤 새 enqueue 연결을 해제하는 순서로 설계합니다. 작업 상태·결과·기존 메모·원본 물품은 보존합니다. 전체 데이터 삭제, 상태 일괄 초기화, `DROP ... CASCADE`, 기존 테이블 재생성은 복구안에 넣지 않습니다. 새 객체 제거는 의존성과 기존 동일 이름 객체의 소유권을 확인한 후 별도 검토해야 합니다. 현재 없는 ZIP 롤백을 안전하다고 인정하거나 운영용으로 새로 확정하지 않았습니다.

**2차 검증 리포트 — 실제 수행 범위**

원본 `tests/test_logic.cjs`는 통과했습니다. 해당 검사는 TS transpile, 두 순수 함수의 일부 예시, SQL 문자열 존재 확인입니다. PostgreSQL 트리거 실행·다중 세션 경합·실제 인증·Cron·배포·Gemini 성공 검사가 아닙니다. transpile도 Deno 타입 검사와 같지 않습니다.

추가한 `reproduce.cjs`는 24개 관측 항목을 생성합니다. 결함의 반례와 정상 동작을 함께 확인했습니다. **재현 검사가 통과했다는 것은 원안의 결함이 수정됐다거나 운영 자동화가 검증됐다는 뜻이 아닙니다.**

| 검증 영역 | 실제 수행 | 한계 |
| --- | --- | --- |
| 로직 | 정상 저장, 원문/메모 보존, 중복 finish 거부, 재시도 간격·상한 | 저장소 초기 스키마를 사용한 로컬 DB |
| 엣지 케이스 | 경로 변경, lease 만료 복구, 수령 후 재개 누락, 같은 경로, 잘못된 전체 URL, 부정 표현, 파일럿 대상 불일치 | 실제 외부 사진·수집 API는 사용하지 않음 |
| 보안 | 익명 private 권한 거부, 비담당자 private 행 없음, 공개 상태 컬럼 노출, 담당자의 AI 컬럼 직접 변경 | auth.uid/storage/cron은 스텁. 운영 담당자별 권한 미검증 |
| Dry Run | worker 핸들러 정상/인증 실패/AI 실패를 HTTP·DB 스텁으로 검사 | 실제 Supabase Edge 런타임 통합 검사 아님 |
| 이미지 | 7,999,999 / 8,000,000 허용, 8,000,001 / 8,388,608 거부, 원격 GIF/HEIC 거부 | 합성 JPEG 시그니처 사용. 실제 이미지 디코딩·모델 성공 검증 아님 |
| SQL | 새 읽기 전용 SQL 3개 로컬 실행, 원본 preflight 오류 재현, 원본 코어 DDL·RPC 실행 | PGlite 0.5.16 / PostgreSQL 18.6. 운영 PG 버전과 동일하다고 가정하지 않음 |
| 동시성 | 즉시 연속 claim 2개, lease 이전 결과 차단 | 다중 세션 동시 트랜잭션·부하 시험은 하지 않음 |

기존 파일에는 수정을 가하지 않았고, 새 SQL/검사/문서에는 `고현 수정 시작 / 고현 수정 끝` 표기를 넣었습니다. 새 진단 SQL은 모두 `BEGIN READ ONLY`와 statement timeout을 사용하며, 키·메모·개별 물품 값·Vault 비밀값·Cron 명령 원문을 출력하지 않습니다. 기존 SQL 파일을 대체하지 않습니다.

재현 방법은 같은 브랜치에서 ZIP을 별도 폴더에 해제한 뒤 다음과 같습니다. 종속성은 저장소 밖 임시 폴더에 설치합니다.

```sh
EEUM_AUDIT_DEPS=/tmp/eeum-photo-ai-audit
npm --cache "$EEUM_AUDIT_DEPS/cache" install --prefix "$EEUM_AUDIT_DEPS" --ignore-scripts --save-exact @electric-sql/pglite@0.5.16 typescript@5.9.3
NODE_PATH="$EEUM_AUDIT_DEPS/node_modules" node audit/photo-ai/reproduce.cjs /path/to/unzipped-C-draft
NODE_PATH="$EEUM_AUDIT_DEPS/node_modules" node /path/to/unzipped-C-draft/tests/test_logic.cjs
```

**운영 확인에 필요한 다음 자료**

- `01_readonly_catalog.sql`: 컬럼·제약·인덱스·RLS·GRANT·기존 트리거/함수 식별자·확장 존재 확인. 먼저 이 결과를 확인해야 합니다.
- `02_readonly_counts_and_storage.sql`: 필요한 컬럼이 있는 것을 확인한 뒤 전체 DB 범위와 Storage 크기/MIME·버킷 설정을 집계합니다. 프로젝트 URL은 현재 저장소 CONFIG 기준입니다.
- `03_readonly_scheduler.sql`: 첫 파일에서 Cron/Vault 존재를 확인한 뒤 이름·스케줄·명령 해시와 Vault 이름별 개수만 조회합니다. 비밀값을 조회하지 않습니다.
- 실제 배포된 `ai-parse`, `fetch-police-items`의 비밀값 제거 소스 또는 커밋/소스 해시, JWT 검증 설정, 필요한 환경변수의 존재 여부가 필요합니다. 비밀키·DB 비밀번호는 채팅으로 전달할 필요가 없습니다.

이 자료를 대조한 뒤 최소 변경 범위와 복구 SQL을 확정할 수 있습니다. 운영 DB 변경·실제 파일럿을 위한 쓰기·Edge Function 배포·push는 현재 수행 범위에 포함하지 않았으며, 사용자가 지정한 사전 승인이 필요한 단계로 남아 있습니다.
